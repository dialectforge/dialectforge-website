DialectForge VPN Offline

A VPN built on the DialectForge protocol. The service is offline right now, and the code is being prepared for open-source release under AGPL-3.0. There are two versions: the current apps, which use an earlier protocol, and DF-VPN v1, which is in testing and not yet released.

§ 1 On the wire

What your ISP sees

Here's the same kind of capture a packet analyzer shows, the same kind of tool used to detect and block VPNs. Top: WireGuard. Bottom: an example of the earlier DialectForge protocol used by the current apps. DF-VPN v1 traffic does not look like this yet.

Why it matters

Countries like China and Iran use deep packet inspection to fingerprint and block VPN protocols. If traffic has a recognizable pattern, it can be blocked. The earlier DialectForge protocol, used by the current apps, was designed to avoid a fixed pattern. DF-VPN v1 does not include that traffic shaping yet. It is planned for a later version. None of this has been tested against a real censor.

How it was built

Current apps (earlier protocol): clients were built for macOS, Windows and iOS, with Android in progress. They negotiate a shared dialect over a control channel, wrap every packet in it, and refresh the dialect every 120 seconds. They do not use post-quantum cryptography. They are built on an XOR-seed scheme, and the DF-VPN v1 spec says an XOR keystream must not be used as encryption. DF-VPN v1 (in testing, not yet released) replaces that protocol. None of the released apps run v1 yet. When the code is released you'll be able to work toward running your own server (see Run it yourself). See the protocol for the details.

Where the security comes from

DF-VPN v1 (in testing, not yet released): the security comes from standard cryptography. Every handshake, and every rekey every 120 seconds, uses a hybrid post-quantum key exchange (X-Wing, which combines ML-KEM-768 and X25519) together with X3DH. Traffic is encrypted with AES-256-GCM, keys are derived with HKDF-SHA256, and there is no fallback to a weaker mode. Authentication is classical only (static X25519 identity keys), so v1 does not have post-quantum authentication. That is a stated non-goal for v1. Current apps (earlier protocol): no post-quantum key exchange. In the earlier protocol, dialect hopping was an extra layer meant to resist fingerprinting, not the source of the security. This is not security through obscurity.

What's been tested

On October 21, 2026, the DF-VPN v1 test suite passed on my own machine (in WSL): 47 of 47 test vectors, 30 of 30 security tests, 41 of 41 leak and kill switch tests, 4 of 4 end-to-end tests, 8 of 8 rate limit tests and 36 of 36 rate limiter unit tests. These results are self-tested, with help from AI assistants, and not yet independently reviewed. Passing my own tests is not the same as an outside security audit.

Service status: offline

There's no live DialectForge VPN service right now, and nothing to subscribe to. Existing download links are disabled. Questions: help@dialectforge.com.

§ 2 Run it yourself

Run it yourself

DialectForge LLC doesn't run any VPN servers anymore. The server and client source code will be published as open source under AGPL-3.0 in the repository dialectforge/dialectforge-vpn-oss. It isn't public yet.

What self-hosting involves

PartWhat it is and what it needs
ServerAuth API + VPN handler

A Python (FastAPI) account and device API backed by PostgreSQL, with an installer for Ubuntu 22.04, plus a Python handler that relays the encrypted VPN traffic through a Linux TUN device with NAT. Needs a Linux server with root access and your own TLS certificate. The open-source release will state which protocol version it contains.

iOS / macOSSwift apps with a packet tunnel

Xcode and an Apple Developer account with the Network Extension entitlement.

AndroidKotlin app

The Android SDK; builds with Gradle.

Windows.NET 8 app

The .NET 8 SDK and the third-party Wintun driver, which isn't included.

  1. Set up the server

    Install the auth API and database, then run the VPN handler.

  2. Point the clients at it

    The server address is set in the client code, so you change it and build the apps yourself.

  3. Sign and install

    Use your own signing identities and keys. None of the old ones are included.

Not complete yet

Some pieces still need work before this runs end to end. Most importantly, the negotiation service the clients connect to first isn't in the repository yet. There's also no service file for the VPN handler, and some settings are hardcoded. The repository's self-hosting guide lists them. The code hasn't been independently security-reviewed.

The shop's closed, but the plans and the jigs are going on the table so you can build your own. A couple of jigs are still on the bench.
