Verify Shelved

When a module breaks, know exactly which proofs are still trustworthy. This project is shelved. The concept and API design are documented here for reference, and no service is running.

§ 1 Problem

Without Verify

  • A component regresses
  • You re-run everything from scratch
  • Hours of SMT solving
  • Every proof is suspect until re-proven

With Verify

  • A component regresses; you revoke it
  • The dependency graph is walked
  • “3 proofs scarred, 7 preserved”
  • You fix only what's affected

  1. Register modules

    Each component (parser, compiler, prover, backends) gets a seed-scoped isolation boundary.

  2. Register theorems

    Every proof is registered with its lineage back to the modules that produced it.

  3. Revoke

    When a module regresses, revoke its seed. Affected theorems are marked as scarred.

  4. Blast radius

    An immediate report of which proofs are scarred and which are preserved.

If one tool in the shop turns out to be out of true, you only re-check the pieces that tool touched, not the whole house.

§ 2 API design
# Health check
GET  /health

# Initialize a verification context
POST /api/v1/init
  { "master_seed": "my-project-audit-2026" }

# Register a module
POST /api/v1/modules/register
  { "context_id": "...", "module_id": "smt_solver", "version": "4.8.0",
    "description": "Z3 SMT solver", "bond_type": "command" }

# Register a theorem with lineage
POST /api/v1/theorems/register
  { "context_id": "...", "theorem_id": "transfer_safe",
    "name": "Transfer No Overflow", "verified_by": "smt_solver",
    "description": "...", "depends_on": ["vc_generator"] }

# Revoke a module and get blast radius
POST /api/v1/revoke
  { "context_id": "...", "module_id": "vc_generator",
    "reason": "Storage aliasing regression in v4.8.0" }

# Response: { "directly_scarred": 3, "preserved": 7, "total_theorems": 10 }
