Mesh / Tunnel

Server-to-server and database traffic, wrapped in DialectForge. The database connects to a local port and has no idea its traffic is crossing the internet in dialect.

§ 1 Before / after
§ 2 How

  1. Built into the server

    Mesh runs as a service on each machine. When servers come online their tunnel endpoints negotiate a dialect that only they share. There's no external auth service.

  2. Replication through the tunnel

    The primary runs a tunnel endpoint; each replica connects through it. The database software just talks to a local address.

  3. The mesh secret never crosses the wire

    All servers share a mesh secret, but it's never transmitted. Endpoints exchange nonces and derive a unique session seed for each connection, so capturing packets shouldn't let you rebuild the secret.

  4. Session-mode dialects

    Replication is a continuous stream, and changing dialect mid-stream could corrupt data. So each tunnel connection holds its dialect for the life of the session, and new connections negotiate new ones.

I ran my own servers this way: user data and replication streams between machines on three continents went through DF tunnels. If it's good enough for the people using it, it should be good enough for my own infrastructure.
