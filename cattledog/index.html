DialectForge / Cattledog

Cattledog Open source · Apache-2.0

Cattledog wraps any LLM with two ideas from Lu: honesty, meaning an answer that can't be grounded becomes “I don't know”, and scars, memories of forbidden actions and past mistakes that block matching tool calls before they run. It's Apache-2.0, so anyone can use it, including companies, for free.

§ 1 The idea

A dog for the herd, not a new herd

Lu tried to be the whole AI. Cattledog doesn't. It sits between an LLM and the world and does two jobs: it decides which of the model's actions are allowed, and it checks whether the model's answers are grounded. It's a client of a small Lu brain that it owns (a sandbox brain). It never changes the model itself, so it works with any model. The proof of concept uses a local model through Ollama.

The AI can bark all it wants. The dog decides which gates open, and it double-checks the work.

§ 2 Architecture
§ 3 Step by step

How it works

  1. Teach it what's forbidden

    You register capabilities (tools) in the sandbox Lu and scar the ones that are forbidden. A scar makes a capability structurally unreachable: the data stays, but every path to it is cut, and every block names the scar that caused it.

  2. Gate every tool call

    Before any tool runs, the gate checks it in layers: tools that are banned outright (such as run_shell), a default-deny allowlist (an unknown or renamed tool is blocked), semantic scars (dense BGE-small embeddings of forbidden end states, matched by similarity), and a composition policy for dual-use tools (for example, “read a private file, then send it outside” counts as exfiltration). Obfuscated payloads (base64, hex, URL encoding, l33t) are decoded before matching.

  3. Check every answer (“off-ness”)

    After the model answers, Cattledog asks Lu for the most relevant fact it remembers. If the answer conflicts with that fact or isn't grounded by it, the answer is sent back. After a capped number of tries, the answer becomes an explicit “I don't know”. Cattledog never just accepts the last guess.

  4. Keep revoked things out

    A kill switch watches what comes back from tools and retrieved passages. A revoked capability named under another alias is still blocked, and so is a revoked fact that comes back in different words (it normalizes numbers, look-alike letters and attribute slots).

§ 4 Code

From the repository

The heart of the answer mediator (orchestrator/answer_mediator.py, trimmed):

while off and loops < self.cap:
    loops += 1
    candidate = self._ask_base(
        'An independent reference could not corroborate this. '
        'If you cannot verify it, reply exactly "UNSURE". ...')
    if candidate.strip().upper().startswith('UNSURE'):
        break
    final = candidate
    off, ev = self._offness(question, final)
if off:
    final = '[IDK] I cannot verify this confidently, so I will not assert an answer.'

The first two layers of the tool gate (orchestrator/hybrid_gate.py):

TOOL_IDENTITY = {'run_shell'}          # banned outright
# default-DENY unknown tools. Only these tools may run.
ALLOWED_TOOLS = {'get_weather', 'get_time', 'calculator', 'list_directory', ...}
§ 5 Design choices

Why it's built this way

  • Outside the model: no fine-tuning and no access to weights, so it can wrap any model, local or hosted.
  • Default deny: an unknown tool is blocked. Renaming a tool doesn't get around the gate.
  • Refuse instead of guess: “I don't know” is a valid final answer. Accepting the model's last guess is not.
  • Every block is explained: each refusal names the scar or rule behind it, so you can audit it.
  • Apache-2.0: safety tooling should be easy for anyone to adopt, including companies.
§ 6 Tested vs unproven

What's tested, and what isn't

In my own runs, with small local models on one Windows PC:

  • Capability gate demo: two different jailbreaks made the model call forbidden tools. Without the gate, the calls ran. With it, they were all blocked and nothing executed.
  • Agentic red-team harness: of 101 valid attack trials where the bare model misbehaved, the full stack blocked and neutralized 100. But most of those blocks came from the tool denylist, not from the semantic scars generalizing.
  • Kill switch reintroduction suite: 17 of 17 as specified, with one known gap. A restatement that drops both the subject and every distinctive detail isn't caught.
  • The Rust side builds and its tests pass.

Unproven: nobody has reproduced any of this independently. The semantic scars don't reliably separate exfiltration from benign email, because they overlap in embedding space. A blind evasion run reported 0 of 27 leaks, but that number is confounded: many attacks never happened because the weak model couldn't produce the tool calls. It has only been tested on Windows with Ollama. It is not a security product. Don't rely on it to stop a determined attacker or to remove hallucinations. The docs/ folder in the repository has every finding, failures included.

§ 7 Run it

How to run it

git clone https://github.com/dialectforge/cattledog
cd cattledog/rust/v2 && cargo build --release   # builds lu_mcp_v2_cd
cd ../..
ollama pull llama3.1:8b
mkdir -p logs
python demo/demo_capability_gate.py

Paths are resolved from the repository root. Set CD_ROOT to use a different root, and LU_BIN_DIR if the binaries live somewhere else. With an AI coding assistant, start from AGENTS.md or the prompts on Build with your AI.
