One bug shouldn't break all trust.

Proof checkers verify that software is correct. But when the checker itself has a bug, every theorem it ever approved becomes suspect. DialectForge Verify contains the damage so one bug doesn't cascade into a full re-audit.

The Problem

37 years, still unsolved

Proof assistants like Lean, Coq, and Bend2 rely on a trusted kernel to verify theorems. When a soundness bug is found in any part of that kernel, there's no way to know which theorems were affected. The only option is a full re-audit of every theorem ever verified. For a project like Mathlib with over a million lines of formalized math, that's catastrophic.

The industry response: make the checker smaller

For decades, the answer has been to shrink the trusted kernel and try to prove it correct. Lean was built because Coq had bugs. Then Lean 4 got soundness bugs too. The Lean4Lean project is now trying to verify the verifier. It's checkers all the way down, and bugs still get through.

The Solution

Module Isolation

Each proof checker module (equality checker, type checker, consistency checker) runs in its own seed-derived scope. A bug in one module can't contaminate another because cross-module state access is structurally impossible — not blocked by a guard, but inexpressible in the module's dialect.

Theorem Lineage

Every verified theorem is stamped with which module verified it, when, and with what seed. When something goes wrong, you know exactly which theorems were touched by the affected component.

Surgical Revocation

When a bug is found, you revoke that module's seed. Only the theorems it verified get scarred. Theorems that depend on scarred theorems get transitively scarred. Everything else stays verified. Zero full re-audits.

How It Works

  1. Install the SDK. Add the DialectForge Verify client library to your proof checker project. One dependency, no configuration.
  2. Register your modules. Tag each component of your proof checker (equality, type checking, consistency). A few lines at startup.
  3. Hook the boundaries. Add a verification call where one module calls another. One line per boundary. Your team knows where these are.
  4. Theorems get tracked automatically. Every verified theorem is logged with which module checked it and when. This happens in the background.
  5. When a bug is found, revoke. One API call. The system identifies every affected theorem, marks them as scarred, and preserves everything else.
