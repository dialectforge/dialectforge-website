Verify Open-sourcing

When a module breaks, know exactly which proofs are still trustworthy. This project isn't being run as a service. Instead it's being released as open source, and the concept and API design are documented here. There's no hosted service.

§ 1 Problem

Without Verify

  • A component regresses
  • You re-run everything from scratch
  • Long SMT solving runs
  • Every proof is suspect until re-proven

With Verify

  • A component regresses; you revoke it
  • The dependency graph is walked
  • “3 proofs scarred, 7 preserved”
  • You fix only what's affected

  1. Register modules

    Each component (parser, compiler, prover, backends) gets a seed-scoped isolation boundary.

  2. Register theorems

    Every proof is registered with its lineage back to the modules that produced it.

  3. Revoke

    When a module regresses, revoke its seed. Affected theorems are marked as scarred.

  4. Blast radius

    An immediate report of which proofs are scarred and which are preserved.

If one tool in the shop turns out to be out of true, you only re-check the pieces that tool touched, not the whole house.

§ 2 API design
# Health check
GET  /health

# Initialize a verification context
POST /api/v1/init
  { "master_seed": "my-project-audit-2026" }

# Register a module
POST /api/v1/modules/register
  { "context_id": "...", "module_id": "smt_solver", "version": "4.8.0",
    "description": "Z3 SMT solver", "bond_type": "command" }

# Register a theorem with lineage
POST /api/v1/theorems/register
  { "context_id": "...", "theorem_id": "transfer_safe",
    "name": "Transfer No Overflow", "verified_by": "smt_solver",
    "description": "...", "depends_on": ["vc_generator"] }

# Revoke a module and get blast radius
POST /api/v1/revoke
  { "context_id": "...", "module_id": "vc_generator",
    "reason": "Storage aliasing regression in v4.8.0" }

# Response: { "directly_scarred": 3, "preserved": 7, "total_theorems": 10 }

The core server is being prepared for release under AGPL-3.0, and a client SDK is already public: dialectforge-verify. Contact: john@dialectforge.com.

§ AI Agent

Start with an AI agent

Paste this into your AI coding agent. It points the agent at the repository's AGENTS.md (what's there, what works, which files to read first), the protocol notes and the license, then has it plan the integration with you.

I want to integrate the DialectForge protocol (Verify) into my project. Before writing any code, read these in order:
1. AGENTS.md in https://github.com/dialectforge/dialectforge-verify-core
2. https://dialectforge.com/protocol/
3. LICENSE, COMMERCIAL-LICENSE.md and CONTRIBUTING.md in that repository
Then ask me about my project (language, where data moves, what I want to protect) and propose a small integration plan for me to approve.
Treat every security property as a design goal: this code has not been independently audited. Tell me about the license obligations (AGPL-3.0, or a commercial license from DialectForge LLC) before copying any of its code into my project.

Repository: dialectforge/dialectforge-verify-core. It is private while it is being cleaned up and will be public soon; the prompt works as-is once it is. All agent prompts.

It's like handing a new helper the drawings and the spec sheet before they pick up a saw.
